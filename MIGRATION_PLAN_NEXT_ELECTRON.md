# План миграции на Next.js + Electron (без отдельного backend в runtime)

## 1) Цель
- Перевести проект с `Django + React/Vite` на единый стек `TypeScript`.
- Убрать отдельный backend-процесс в конечном `exe`.
- Все расчеты выполнять на фронте (клиентский TS), графики строить локально.
- Итог: запуск через `SMTU-TAU.exe` без поднятия API на `localhost:<port>`.

## 2) Текущее состояние
- Фронт: `FrontEnd` (React + Vite).
- Бэкенд: `Backend` (Django, вычисления в `Backend/labs/directions/*`).
- Текущий `exe` собирается через `PyInstaller` (`build_exe.ps1`) и запускает Python-часть.

## 3) Целевая архитектура
- `Next.js` как UI-слой и маршрутизация (только static export).
- Без `API routes`, `Server Actions`, SSR.
- Расчеты: модуль `src/modules/calculations/*` на TS.
- Тяжелые расчеты: `Web Worker` (`src/workers/*`) для отзывчивого UI.
- Desktop-оболочка: `Electron`.
- `Electron` открывает локальный HTML (`out/index.html`) через `loadFile`, а не URL.

## 4) Ограничения и правила
- В runtime нельзя зависеть от локального HTTP-сервера.
- Секреты и закрытые ключи нельзя хранить на клиенте (если появятся такие требования, потребуется сервер).
- Для математической точности обязателен этап сверки Python vs TS по эталонным тестам.

## 6) Пошаговый план миграции

### Этап 0. Подготовка и фиксация эталона
- Зафиксировать текущую ветку как baseline.
- Составить карту всех лабораторных и входных/выходных параметров из Python-модулей:
  - `Backend/labs/directions/tau_basics/lab1.py ... lab5.py`
  - `Backend/labs/directions/tau_lin/lab1.py ... lab4.py`
  - `Backend/labs/directions/tau_nolin/lab1.py ... lab5.py`
  - `Backend/labs/directions/TDZ/lab1.py ... lab6.py`
- Подготовить набор эталонных кейсов (JSON) с ожидаемыми результатами.

Критерий готовности:
- Есть таблица "модуль -> вход -> ожидаемый выход".
- Есть минимум 5-10 эталонных кейсов на каждую лабораторную.

### Этап 1. Каркас Next.js (static mode)
- Создать новый Next.js проект на TS.
- Настроить `next.config.mjs` для статического экспорта:
  - `output: 'export'`
  - `images.unoptimized: true`
- Перенести базовый layout и навигацию из текущего фронта.
- Подключить библиотеку графиков (`echarts` или `uPlot`).

Критерий готовности:
- Приложение собирается в статические файлы (`out/`).
- Основные страницы открываются без API.

### Этап 2. Порт вычислительного ядра Python -> TypeScript
- Создать типизированный слой:
  - `Input`/`Output` типы на каждую лабораторную.
  - Чистые функции без доступа к DOM/React.
- Переносить расчеты по направлениям:
  1. `tau_basics`
  2. `tau_lin`
  3. `tau_nolin` (+ нелинейности)
  4. `TDZ`
- На каждый портированный модуль написать unit-тесты и сравнение с эталоном (погрешность `epsilon`).

Критерий готовности:
- Все лабораторные дают результаты в допустимой погрешности относительно Python-версии.

### Этап 3. Интеграция с UI и графиками
- Перевести формы ввода на `react-hook-form` + `zod` (или эквивалент).
- Результаты считать на клиенте и сразу визуализировать.
- Тяжелые расчеты вынести в `Web Worker`.
- Добавить состояния: `loading/error/empty`.

Критерий готовности:
- Графики и таблицы обновляются без лагов на целевых объемах данных.

### Этап 4. Electron-оболочка без порта
- Добавить `electron/main.ts` и `electron/preload.ts`.
- В `main.ts` загружать локальный файл:
  - `mainWindow.loadFile(path.join(..., 'out', 'index.html'))`
- Настроить безопасность:
  - `contextIsolation: true`
  - `nodeIntegration: false`
  - доступ к Node только через `preload`.

Критерий готовности:
- Приложение запускается как desktop-окно, без запуска API или Next server.

### Этап 5. Сборка `exe`
- Подключить `electron-builder`.
- Настроить `win`-таргеты (`nsis` или `portable`).
- Добавить команды:
  - `npm run build:web` -> собирает `out/`
  - `npm run build:desktop` -> собирает `exe`
- Обновить CI/CD или локальный скрипт сборки (замена `build_exe.ps1`).

Критерий готовности:
- Получается рабочий `SMTU-TAU.exe`/`Setup.exe`, который запускается на чистой Windows-машине.

### Этап 6. Финальная валидация и вывод legacy
- Пройти регрессионный чек-лист по всем лабораторным.
- Сравнить производительность и точность с текущей реализацией.
- После подтверждения удалить `Backend`/старый `FrontEnd` из основной ветки (или перенести в `legacy`).

Критерий готовности:
- Полный функциональный паритет.
- Нет runtime-зависимости от Python/Django.

## 7) Риски и меры
- Риск: расхождения в численных расчетах Python vs JS.
  - Мера: golden-тесты и фиксированная погрешность `epsilon`.
- Риск: подвисания UI на тяжелых расчетах.
  - Мера: `Web Worker` + батчинг/дискретизация данных для графиков.
- Риск: слишком большой размер инсталлятора.
  - Мера: минимизировать зависимости, включить сжатие в `electron-builder`.

## 8) Минимальный MVP порядок (если делать быстро)
1. Next static каркас + 1-2 ключевых лабораторных на TS.
2. Графики + worker для этих лабораторных.
3. Electron запуск через `loadFile`.
4. Сборка первого `exe`.
5. Поэтапный перенос остальных лабораторных.

## 9) Definition of Done
- Все лабораторные из текущего `Backend/labs/directions` перенесены на TS.
- В runtime не запускается отдельный сервер/API.
- Desktop-приложение стартует из `exe` и работает оффлайн.
- Точность расчетов подтверждена тестами и ручной сверкой.
